# Godot 独立游戏从零到一 Recipe

> 适用于当前项目：固定关卡、搜索资源、敌人持续增强、限时撤离的 2D 独立游戏方向。
>
> 目标不是“把功能做完”，而是持续证明：玩家在这个世界里做选择、承担风险并获得反馈时，会觉得有趣，并且愿意再来一局。

## 0. 先确定路线：不是二选一，而是“玩法先行、视觉并行”

你提出的两条路都抓住了一部分真相：

- 极简 Demo 能最快验证游戏是否好玩，成本低、反馈真实。
- 先做画面能帮助作者确认审美、氛围和最终愿景，避免做出“功能正确但没有灵魂”的作品。

但如果完全先做美术，再围绕素材设计玩法，最容易出现两个问题：

1. 画面很漂亮，但核心操作没有有趣的决策，最后只能不断堆系统救场。
2. 美术资产的制作成本会让你舍不得删掉错误方向，形成沉没成本。

本项目采用第三条路线：

> **先用极简占位物验证核心乐趣；同时尽早制作一张低成本视觉目标图；在核心循环成立后，用一个可玩的“视觉垂直切片”统一玩法、美术、声音和节奏。**

所谓“视觉目标图”，可以是 GPT-image-2 生成的概念图、色板、构图参考和 UI 草图；它用来确认方向，不直接等同于最终游戏资产。

推荐顺序：

```text
核心假设
  → 纸面/口头规则
  → 灰盒玩法原型
  → 低成本视觉目标图
  → 可玩垂直切片
  → 内容生产
  → 外部测试
  → 打磨、优化、发布
```

## 1. 一款优秀独立游戏最根本的原则

### 原则一：先定义“玩家反复做什么，以及为什么还想再做一次”

优秀游戏通常不是功能最多，而是核心动作具有清晰的因果关系：

```text
玩家看见信息 → 做出取舍 → 执行行动 → 承担风险 → 得到反馈/奖励 → 形成新局面
```

对本项目而言，核心问题不是“有多少敌人、宝箱和装备”，而是：

> 玩家在资源有限、敌人不断增强、撤离时间有限的情况下，是否会不断思考“我还能再搜一个房间吗？”

这句话就是项目的体验支柱。所有系统都应服务于它；不能服务于它的内容，先不做。

### 原则二：每个系统都必须制造选择，而不只是增加内容

系统的价值不在于它存在，而在于它是否让玩家做出有意义的决定。

| 系统 | 有价值的设计问题 | 无效的设计倾向 |
|---|---|---|
| 搜索 | 继续深入还是立即撤离？ | 只是走到物品旁按键 |
| 装备 | 当前局带什么，如何适配本关？ | 只有数值更高的替换品 |
| 敌人 | 绕行、战斗、利用环境还是冒险穿越？ | 只会追着玩家碰撞 |
| 视野 | 信息不足时如何判断风险？ | 单纯让玩家看不清 |
| 撤离 | 如何规划路线和时间？ | 最后突然出现倒计时 |

### 原则三：反馈必须及时、明确、可归因

玩家应当知道：发生了什么、为什么发生、自己的行为是否有效。

每个重要动作都至少要有一项反馈：动画、音效、粒子、数字、镜头变化、UI 变化或敌人状态变化。失败也必须让玩家理解原因，而不是觉得系统在作弊。

### 原则四：范围控制是品质的一部分

第一款独立游戏的“优秀”，首先意味着完成一个小而完整、可被别人玩懂和记住的体验。

项目范围按以下优先级管理：

```text
核心循环 > 可读性与手感 > 一种完整关卡体验 > 内容数量 > 复杂系统 > 装饰性细节
```

任何新想法先问：它是否强化核心循环？如果不能在一句话中说明强化方式，就放入备选清单，而不是立即开发。

### 原则五：以可玩版本为事实，以文档为假设

设计文档是预测，不是合同。每次玩起来后，都允许推翻原来的数值、流程和系统。保留决策记录，但不要为了维护旧设计而牺牲玩家体验。

## 2. 项目总流程与阶段门

每个阶段都必须有一个可运行的产出和一个明确的“继续/修改/砍掉”判断。

### Phase 1：一句话定位与体验支柱

产出：`1.page vision`，不超过一页。

必须写清：

- 玩家是谁，扮演谁。
- 玩家每局最主要做什么。
- 最有吸引力的矛盾或取舍是什么。
- 一局预计多长。
- 玩家希望反复体验的情绪是什么。
- 本项目明确不做什么。

当前项目的临时定位可以是：

> 一款低操作负担、重路线判断的搜索撤离游戏：玩家在逐渐失控的关卡中搜集资源，决定何时放弃贪心并活着离开。

验收标准：你能在 30 秒内向别人说明“这游戏为什么值得玩”，并且没有依赖“以后会加入很多内容”来解释乐趣。

### Phase 2：核心循环灰盒原型

只使用 Godot 基础节点、色块、文字和简单几何图形，实现一局最小闭环：

1. 玩家移动、观察和交互。
2. 至少一个可搜索目标。
3. 至少一种资源或临时强化。
4. 至少一种会制造压力的敌人/风险。
5. 资源越多，风险或时间成本越高。
6. 玩家可以主动撤离，也可以失败。
7. 一局结束后能看到结果，并能立即重开。

第一版不要做：背包大系统、复杂装备树、多个关卡、完整美术、剧情、存档、联网和大量敌人变体。

验收标准：在 3 分钟内，玩家至少做出三次“继续搜索/现在撤离”的判断；不看代码也能理解自己为什么成功或失败。

### Phase 3：手感与可读性

在增加内容前，先处理：

- 移动速度、加速度、碰撞和转向。
- 交互距离、输入缓冲、攻击/受击时机。
- 敌人追踪、预警和脱离规则。
- 摄像机跟随、视野遮挡和重要信息层级。
- 伤害、资源、时间等状态的反馈。

验收标准：连续玩五局，主要问题不再是“操作很别扭”或“我不知道发生了什么”。

### Phase 4：建立视觉方向，而不是先堆最终资产

此阶段使用 GPT-image-2 或其他工具生成：

- 3—5 张风格探索图。
- 一张场景构图/光照目标图。
- 一套色板、材质和形状语言。
- 玩家、敌人、宝箱、撤离点的识别草图。
- 一张 HUD/菜单草图。

生成图的作用是回答“我们想让玩家感受到什么”，而不是直接决定玩法。要把概念图拆解为可实现的视觉规则：镜头角度、主要色彩、轮廓对比、光源、动画节奏、信息优先级。

验收标准：即使所有资产都还是占位符，你也能说清最终游戏的视觉承诺；并且这个视觉方向不会降低可读性。

### Phase 5：垂直切片

只做一个完整、短小、可独立体验的关卡或场景，包含：

- 最终目标的玩家控制与相机。
- 一组接近最终品质的环境资产。
- 一个完整的搜索—风险—撤离循环。
- 至少一种敌人和一种特殊关卡特性。
- 基本 UI、音效、音乐氛围和失败/成功反馈。

垂直切片不是宣传片，而是一个可以让陌生玩家真实游玩的样品。它用来验证“玩法、美术、声音组合起来是否成立”。

验收标准：让 3—5 名不了解项目的人试玩；他们能独立完成一局，并且能复述核心取舍。记录他们的行为，不只听他们说“好不好看”。

### Phase 6：内容生产与系统收敛

只有垂直切片成立后，才扩展关卡、敌人、装备和长期成长。

内容生产应优先增加“不同的决策”，而不是增加“更多同样的房间”。每个新内容都要写出它改变了哪种策略、制造了什么新风险、与现有内容如何组合。

当系统开始互相叠加时，优先使用数据资源、信号和清晰的模块边界，让数值可调、场景可复用、规则可测试。

### Phase 7：测试、打磨与发布

固定进行三类测试：

- 自测：功能是否正确，是否有阻塞和崩溃。
- 观察测试：玩家是否看懂、是否按预期行动。
- 体验测试：玩家是否愿意再玩、是否记得核心乐趣。

每轮只挑 1—3 个最高价值问题修复。发布前优先保证：开局理解成本低、失败原因清楚、性能稳定、输入和音量可配置、关键流程可完成。

## 3. 当前项目的最小可行版本（MVP）

建议把第一目标限制为“一局 5—10 分钟的单场景体验”：

- 一个小型固定地图。
- 一个玩家角色。
- 一种基础攻击或规避方式。
- 一种普通敌人。
- 一种特殊敌人或关卡威胁。
- 三类可搜索对象：普通资源、临时强化、任务道具。
- 一个持续增强的压力来源。
- 一个明确的撤离点和撤离倒计时。
- 成功、失败、重开三个结果流程。

暂不加入永久成长、复杂商店、多个角色、完整图鉴和大量关卡。它们可以在核心循环经过外部测试后再进入路线图。

## 4. 每个开发任务的执行模板

每次开始工作前，写下以下五项：

```text
目标：这次要让玩家体验到什么？
假设：我认为改动后会发生什么？
最小实现：完成验证所需的最少内容是什么？
验收：我如何通过游玩证明它成立？
结论：保留、修改、删除，还是延后？
```

任务应尽量小到半天至两天可以完成，并且每次完成后都能运行游戏验证。不要连续积累一周“理论上已经完成但还没玩过”的代码。

## 5. 与 GPT 协作的边界

GPT 最适合帮助你：拆解系统、提出替代方案、生成脚本初稿、解释 Godot 概念、设计测试清单、生成概念图和风格探索、分析试玩反馈。

你必须亲自掌握：项目目标、核心取舍、场景结构、节点职责、输入与状态流转、为什么删掉某个系统，以及试玩后最终保留什么。

使用 AI 生成代码时，遵循：

1. 一次只解决一个可验证问题。
2. 先让 AI 解释脚本放在哪个节点、输入是什么、输出是什么。
3. 运行并观察结果，再继续扩展。
4. 不复制自己无法解释的复杂架构。
5. 每个阶段保留一个可运行版本，避免大面积返工。

使用 AI 生成美术时，遵循：

1. 先生成方向板，再生成资产。
2. 统一镜头、比例、光照、轮廓和色板。
3. 资产必须服从可读性和玩法信息。
4. 检查版权、授权、模型条款和素材一致性。
5. 最终资产要经过裁切、命名、导入、压缩和 Godot 内测试。

## 6. 最重要的判断口诀

```text
先问玩家在做什么，再问系统怎么实现；
先验证是否好玩，再决定做多少内容；
先建立视觉承诺，再制作大量资产；
先完成一个闭环，再扩展世界；
每次改动都要能被游玩证明。
```

因此，本项目下一步不是生成大量美术，也不是搭建完整架构，而是完成 Phase 1 和 Phase 2：把“贪心搜索—风险增长—及时撤离”的核心循环做成一个能在 Godot 中反复游玩的灰盒原型；与此同时制作少量视觉探索图，确认氛围与识别规则。两者都成立后，再进入垂直切片。
