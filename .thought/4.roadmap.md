# Chest Rush · Roadmap (Top-Level Roadmap)

> What this is: the project’s strategic north star and long-range direction, not a todo list. It captures the critical things we must not lose and the phases we are moving through, updated continuously as the system evolves and discussions change. The todo list answers “what do we do next?” while the roadmap answers “where are we going, and what cannot be dropped?”
>
> Relationship to the recipe: `godot/0.recipe.md` defines the development gates (graybox → feel → visual → vertical slice → content → release) as the process methodology. This document defines the content and system objectives specific to this project. Use both together: the phase gate tells us when a task belongs in the plan, while the roadmap tells us what to do.
>
> Current position: Phase 2 graybox ✅, Phase 3 feel ✅ complete; the immediate next focus is Phase 4 visual direction and the weapon-system refactor (see below).

## I. Top-Level Structural Decisions (Confirmed and not to be overturned unless re-discussed)

### 1. Chapter-based structure, not a single-level theme
One theme = one chapter: one story + one art direction (for example, school, mall, or abandoned village) + multiple levels under that chapter.
- Reason: a single-level theme places too much demand on art production; a chapter lets one set of art assets serve multiple levels and spread the cost.
- Implication: art and maps must be tile-based and combinable — use a single tile set to create a wide variety of flexible maps.
- Connection to the current state: the current ASCII map is already a prototype of a data-driven map system, which aligns with the tile-based direction.

### 2. The weapon (ghost) system must evolve toward “skill-based” design
The current blade / arrow / domain system is only a minimal playable prototype, not the final form. It must be able to evolve smoothly into the ghost skills described in `0.story.md` (grass-rope lifting, starving ghost growth, head-swapping ghost stolen abilities, knocking ghost read-to-stun, etc.).
- Direction: upgrade “weapons” into combinable ghost skills: data (damage, cooldown, range, projectile behavior) + trigger logic hooks (hit, kill, cast, stun callbacks).
- Do not force abstraction too early — following the recipe, we only converge module boundaries once systems begin stacking together and shared patterns become obvious. Add the 4th and 5th ghosts first, then refine interfaces when common behavior appears.
- This is the implementation target of the “improve the attack system” item in 3.next_step.

### 3. Core gameplay is fixed (no more argument on this)
Moving tower defense: passive attacks, numerical comparison, collecting quest items through read-to-grab actions, then exiting through the gate. There is no “greedy retreat” strategy (already disproven in playtests).

## III. Must Do, But Deferred for Now (Anti-forgetting checklist)

> Rule: if we identify something we will definitely need in the future, it goes here with both “why it matters” and “when it should happen.” We should prefer recording too much rather than forgetting something essential. Each item is tagged with the triggering phase; when that phase arrives, it is pulled back into the active plan.

### Gameplay / Systems
- [ ] **Multi-level map system** (P6): a level is a data file (map / starting 3 ghosts / wave table / enemy composition / quest extraction parameters), so changing a level means editing data rather than adding a new code path. Why: chapter-based design requires multiple levels.
- [ ] **Tile-based combinable map system** (P6): a shared tile set creates many layouts, enabling art reuse across a chapter. Why: this is the technical prerequisite of the chapter system.
- [ ] **Level and equipment counterplay adaptation** (P6): each level starts with a fixed set of 3 ghosts, and those ghosts must counter the enemy patterns in that level. Why: this is a core 0.design rule and creates the decision space of “how should I build for this level?”
- [ ] **Cross-level long-term progression** (P6): key items carried out of a level permanently strengthen the player, expand the starting equipment pool, or unlock entries in a bestiary. Why: it creates the long-term retention hook for the search-attack-exit loop and matches 0.design’s direction of “clear levels to unlock a bestiary and gear.”
- [ ] **Enemy mechanics formalization (visible rules)** (P5 onward): each elite ghost has a fixed trigger and move pattern (knocking ghost is heard clearly, head-swapping ghost exposes orientation tells, replacement ghost shows a visible transfer line). Why: 0.story depends on enemies behaving in readable, visible ways instead of just being bigger numbers.
- [ ] **Resurrection bar** (P6 or later): over-strengthening or excessive lingering raises enemy pressure, or warns that the player’s ghosts are losing control. Why: this is a signature 0.story system and turns “resurrection” into a real in-run pressure source.
- [ ] **Enemies also get weapons / skills** (P6): elite ghosts and bosses have unique attack modes. Why: this follows the direction of 3.next_step and enriches the combat layer.

### Long-Term Retention (0.design addiction design pillars, P6 onward)
- [ ] **Fallback reward system** (P6): even when the player loses, they still retain part of their progress to reduce frustration. Why: 0.design states that “fallback rewards reduce failure frustration.”
- [ ] **Gradual difficulty ramp** (P6): difficulty moves from beginner-friendly levels to advanced challenges. Why: 0.design states that “difficulty should scale for both newcomers and experienced players.”
- [ ] **Collection achievements / global bestiary** (P6): clearing levels unlocks bestiary entries and new starting equipment, while repeated challenge runs unlock special global resources. Why: this is a core long-term retention system.
- [ ] **Visible power progression** (P5): firepower and HP growth are presented clearly and intuitively, improving the player’s sense of control. Why: 0.design calls for “visible power progression.”

### Art / Presentation
- [ ] **Full main character animation set** (P5): the priest currently has only an idle 4-frame loop and lacks walk / attack / hurt / death animations. The tiny-rpg Soldier has a full set, but its 100×100 cartoon style does not match the dungeon aesthetic; the recommendation is to either customize it or choose a unified visual direction.
- [ ] **Lock in Phase 4 visual direction** (P4, current): use AI-generated concept art to explore a “horror-comedy + uncanny revival” aesthetic, unifying camera framing, color palette, silhouettes, and information hierarchy. Why: establish the visual promise before spending effort on asset production.
- [ ] **Tile art assets** (P6): create a reusable tile set for each chapter theme. Why: this is the required art format for chapter-based production.
- [ ] **Audio** (P5): low-pressure looping BGM + full-chain sound effects for destruction, kills, collection, and upgrades. Why: this is a core 0.design retention and engagement pillar.

### Engineering / Tools
- [ ] **Web deployment refresh** (ongoing): once gameplay is stable, export the project to gh-pages again so friends can try the newest build. Why: playtest feedback is a lifeline. Trigger: when the current set of changes has accumulated enough to justify collecting feedback.
- [ ] **Save data / persistence** (P6): cross-level progression, bestiary entries, and unlocks need to persist. Why: this is a prerequisite for multi-level long-term play.
- [ ] **Performance and object pooling** (P6 or when lag appears): once there are many enemies or projectiles, create object pools for floating text and bullets. Why: current counts are still small, so optimization should wait until it becomes necessary.

### Explicitly not planned (to avoid scope creep; recipe principle four)
- Large inventory systems, complex equipment trees, full story cinematics, online play, and a large number of enemy variants — none of these should be added before the core loop has been tested externally.

## IV. How to Maintain This Roadmap

1. **It is alive**: whenever a new direction or required item emerges, update this file; the todo list only handles “what to do next.”
2. **“Must do but deferred” belongs in Section III**: this is the primary reason this document exists. Do not keep those thoughts only in your head.
3. **Re-read during phase transitions**: when entering a new phase (for example, P5), review the roadmap and pull any relevant deferred items into the schedule.
4. **If a direction is cut, keep the reason**: when we decide to drop something, note “cut + reason + date” next to the corresponding item to preserve the decision trail (recipe principle five).

## 一、顶层结构决策（已定调，后续不得推翻除非重新讨论）

### 1. 章节制，而非单关主题
一个主题 = 一个**章节**：一套剧情 + 一套美术风格（如高校/商场/荒村）+ 该章节下**多个不同关卡**。
- 理由：单关一个主题对美术要求太高；章节制让一套美术资产服务多关，摊薄成本。
- 推论：**美术与地图必须是瓦片式（tile-based）可拼接**——用同一套瓦片组合出多种灵活地图。
- 现状衔接：当前 ASCII 字符串地图就是"数据驱动地图"的雏形，是瓦片机制的种子，方向一致。

### 2. 武器（鬼）系统要向"技能化"重构
当前刀/矢/域是**最小可玩原型**，不是终态。要能顺滑进化为 `0.story.md` 里的鬼技能
（草绳吊起、饿死鬼吞噬成长、换头鬼偷能力、敲门鬼读条定身等）。
- 方向：把"武器"升级为**可组合的鬼技能**：数据（伤害/冷却/范围/弹道）+ **触发逻辑钩子**（命中/击杀/读条/定身回调）。
- **先不强做抽象**——按 recipe「系统开始互相叠加时才收敛模块边界」，在加第 4、5 只鬼、出现共性时再提炼接口。
- 这是 3.next_step 里"完善攻击系统"的落点。

### 3. 玩法本质（已定，不再摇摆）
移动塔塔防：被动攻击、数值比拼、搜齐任务道具读条、穿门撤离。**不存在贪撤博弈**（已试玩证伪）。

## 三、一定要做 · 但灰盒/当前阶段暂缓（防遗忘清单）

> **规则**：想到"将来必须做"的事就记在这里，写清"为什么重要 + 什么时候做"。**宁可记多，不可漏掉。**
> 每条标注触发阶段；到了那个阶段就把它捞出来排进当时计划。

### 玩法 / 系统
- [ ] **多关卡地图机制**（P6）：关卡=数据文件（地图/开局3鬼/波次表/怪物构成/任务撤离参数），改数据不加关不改代码。**为什么**：章节制下多关是核心生产方式��
- [ ] **瓦片式可拼接地图机制**（P6）：一套瓦片组合多图，服务章节美术复用。**为什么**：章节制的技术前提。
- [ ] **关卡与装备的克制适配**（P6）：每关固定开局 3 鬼，与本关怪物特性形成克制。**为什么**：0.design 核心规则，制造"这关怎么配装"的决策。
- [ ] **跨关长期成长**（P6）：关键道具带出后可永久强化自身/扩开局装备池/解锁图鉴。**为什么**：搜打撤的长线留存钩子，0.design「通关解锁图鉴与装备」的核心方向。
- [ ] **敌人机制化（看得见的规则）**（P5 起）：每只精英鬼有固定触发与手法（敲门听得见、换头看朝向、替身看得见转移线）。**为什么**：0.story 的关键存在方式，让敌人不只是数值堆叠。
- [ ] **复苏条**（P6 或更晚）：过度强化/滞留抬高敌方强度或己方鬼失控预警。**为什么**：0.story 标志性机制，把"复苏"做成局内压力源。
- [ ] **敌人也配武器/技能**（P6）：精英/Boss 有专属攻击模式。**为什么**：3.next_step 方向，丰富对抗。

### 长线留存（0.design 成瘾设计要点，P6 起）
- [ ] **保底收益机制**（P6）：战败也带走部分收益，降低挫败感。**为什么**：0.design「保底收益降低战败挫败感」。
- [ ] **梯度难度**（P6）：新手关到进阶关的难度阶梯。**为什么**：0.design「梯度难度适配新手与进阶」。
- [ ] **收集成就/全局图鉴**（P6）：通关解锁图鉴与全新开局装备，重复挑战解锁全局专属资源。**为什么**：0.design 长线留存体系。
- [ ] **战力成长可视化**（P5）：火力/血量成长的直观呈现，提升掌控感。**为什么**：0.design「战力成长可视化」。

### 美术 / 表现
- [ ] **主角全套动画**（P5）：priest 只有 idle 4 帧，缺 walk/attack/hurt/death。tiny-rpg Soldier 有全套但 100×100 Q 版风格与 dungeon 不搭，**建议定制或另选统一风格**。
- [ ] **Phase 4 视觉方向定调**（P4，当前）：AI 生图探索"恐怖喜剧+诡异复苏"，统一镜头/色板/轮廓/信息优先级。**为什么**：先建视觉承诺再堆资产，避免风格崩掉。
- [ ] **瓦片美术资产**（P6）：按章节主题产出可拼接瓦片集。**为什么**：章节制的资产形态。
- [ ] **音频**（P5）：低压力循环 BGM + 摧毁/击杀/搜集/升级全链路音效。**为什么**：0.design 成瘾设计要点。

### 工程 / 工具
- [ ] **Web 版重部署**（持续）：玩法稳定后重新导出 gh-pages，让朋友玩到新版。**为什么**：试玩反馈是生命线。**触发**：本轮改动累积到值得收反馈时。
- [ ] **存档/持久化**（P6）：跨关成长、图鉴、解锁需要落盘。**为什么**：多关长线的前提。
- [ ] **性能与对象池**（P6 或出现卡顿征兆时）：后期怪多/弹多时飘字与弹体对象池。**为什么**：现在量小不做，超预期再做。

### 明确暂不做（防范围蔓延，recipe 原则四）
- 背包大系统、复杂装备树、完整剧情演出、联网、大量敌人变体——**核心循环未经外部测试前不做**。

## 四、怎么维护这份 roadmap

1. **它是活的**：每次讨论出新方向/新必做项，就更新本文件；todo 只管下一次动手。
2. **"必做但暂缓"一律进第三节**，不许只在脑子里——这是它存在的首要理由。
3. **阶段推进时回读**：进入新阶段（如 P5）先翻 roadmap，把该阶段的暂缓项捞出来排期。
4. **删东西也要记**：砍掉某个方向时，在对应条目注明"已砍+原因+日期"，保留决策痕迹（recipe 原则五）。
